# 前端架构与依赖方向

## 目标

前端架构的目标是让业务变化集中在对应模块中：页面专注呈现与交互，接口契约集中在 `src/api/`，复杂流程集中在 composable、store 或用例函数，展示转换规则可独立测试。

## 依赖方向

```text
页面 / 业务组件
        ↓
composable / store / use case
        ↓
src/api 中的契约类型与请求方法
        ↓
页面邻近 Mock 或真实接口调用
```

- 页面和组件可以调用 composable、store 或用例，也可以导入 `src/api/...` 的类型和方法。
- `src/api/` 只定义契约与请求方法，不承担字段映射、格式化或默认值处理。
- 页面展示转换集中在调用方或页面邻近的 `utils.ts`；局部 UI 状态类型可直接放在组件内。
- `app/` 只组装路由、Pinia、插件和模块，不实现具体业务流程。

## 职责边界

| 区域 | 负责 | 不负责 |
|---|---|---|
| Page | 路由参数、页面布局、组合业务组件 | 大量跨页面状态 |
| Business Component | 表格、表单、弹窗等领域交互 | 直接修改接口契约 |
| Composable | 可复用交互逻辑、请求编排、局部状态 | 全局共享且需要持久化的状态 |
| Store | 跨页面/跨组件共享状态、缓存与统一动作 | 单个组件的临时开关 |
| `src/api/` | 契约类型、请求方法、证据/TODO | 映射、格式化、默认值和页面业务判断 |
| `utils.ts` / Mock | 展示转换、formatter、未接入回退数据 | 全局 UI 提示和 DOM 操作 |

## 复杂度决策

- 单页面、单次加载：页面内局部 `ref`、同级 `mock.ts` 与 `utils.ts` 即可。
- 多组件共享同一页面逻辑：抽取 composable。
- 跨路由共享且需缓存或统一更新：使用 Pinia store。
- 多接口、多步骤或可复用业务动作：定义用例函数，由页面或 store 调用。

不要为了形式将每个页面拆成所有层。抽象的收益应大于阅读和维护成本。
